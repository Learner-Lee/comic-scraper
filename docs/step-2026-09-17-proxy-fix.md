# 修复：manhuagui 走代理连不上

**日期**：2026-09-17
**触发**：「我下载不了」

---

## 一、根因：不是代码，是代理

复现后看到的是 `ReadTimeout`，不是解析错误。逐个域名测连通性：

| 域名 | 走环境代理 | 直连 |
|---|---|---|
| m.manhuagui.com | **超时** | HTTP 200，0.7 秒 |
| i.hamreus.com（图床） | **超时** | 正常 |
| www.8comic.com | HTTP 200 | — |
| manwame.com | HTTP 200 | — |

环境里设了 `http_proxy=http://127.0.0.1:10808`，而 **requests 会自动读这个变量**
（`trust_env` 默认 True）。manhuagui 是华语区站点，翻墙代理的出口到它路由不通，
于是走代理反而连不上。8comic 和 manwame 走代理正常，所以只有 manhuagui 暴露问题。

## 二、修法：让站点声明自己的代理偏好

代理该怎么走是**站点的属性**（它的服务器在哪、代理出口能不能到），所以交给适配器声明：

```python
class ManhuaguiSite(Site):
    prefer_direct = True   # 默认绕开 http_proxy/https_proxy
```

优先级：`--proxy` > `--no-proxy` > 站点的 `prefer_direct` > 环境变量。
显式指定永远优先，用户网络环境不同也能自己覆盖。

配套：

- CLI 三个子命令（`list`/`download`/`probe`）都加了 `--no-proxy`
- probe 会标注「直连，未走环境代理」，一眼看出走的哪条路
- WebUI 加 `COMIC_NO_PROXY=1` 全局强制直连
- **网络异常时直接把话说明白**，不让人自己猜：
  「若设了 http_proxy/https_proxy，有些站点走代理反而不通，试试加 --no-proxy」

## 三、附带查出的第二个问题：早先下的章节缺图

核对本地文件与站点页数，发现 11:00 下的那批各缺 1 张：

| 章节 | 本地 | 站点 |
|---|---|---|
| 第01话 | 7 | 8 |
| 第02话 | 6 | 7 |
| 第07话 | 8 | 9 |
| 第08话 | 9 | 10 |

缺的正是文件名**已被站点编码过**的那类图（如"宣传页"）——即二次编码 bug 的症状，
说明那批是用修复前的代码下的。该 bug 已在上一轮修掉（`quote(path, safe='/%')`）。

重跑 `download -c 1-8` 全部补齐，8 章 69 张与站点页数完全一致。
断点续传在这里正好发挥作用：已有的跳过，只补缺的。

## 四、验证

| 项 | 结果 |
|---|---|
| manhuagui probe | ✓ 53 章，标注「直连」，抽查 3 章首末页全 200 |
| manhuagui 下载 | ✓ 1–8 章补齐，69 张，与站点页数一致 |
| manwame 回归 | ✓ probe 通过 |
| 8comic 回归 | ✓ probe 通过 |
| `--no-proxy` 通用性 | ✓ 对 8comic 同样生效并标注 |

## 五、经验

超时和解析失败要分开看。这次表面是「下载不了」，但报错类型（`ReadTimeout`
而非 `ScrapeError`）已经指明是网络层，按域名逐个测连通性几步就定位了。

所以把这条线索固化进了错误提示——下次再遇到，程序自己会说该试什么。
