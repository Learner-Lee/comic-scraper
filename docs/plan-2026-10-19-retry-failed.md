# Plan：重试本次下载失败的图片

**日期**：2026-10-19
**目标**：下载过程中失败的图片，在本次任务内重新下载。

---

## 一、把范围收回来

上一轮我做的 `repair` 做大了：它联网核对**全部历史章节**、还去动已打包的 zip。
而实际需求是——**只管本次这次下载**：

- 本次下载时哪几张失败了，就重下那几张
- 已经进了 `downloads/` 的 zip 说明当时就下齐了，不用再管

所以不需要联网核对页数：本次任务里失败的图，它的直链、章节目录、序号**都已经
在内存里**，直接重试就行。比联网核对快得多，也不碰任何已完成的数据。

## 二、实现

### 2.1 记录失败清单

现在 `_download_one` 失败只打印一行就算了，调用方只统计成功数。改成把失败项
收集起来：

```python
@dataclass
class Failure:
    chapter: str   # 章节名（显示用）
    dest: str      # 章节目录
    idx: int       # 图片序号
    url: str       # 直链
```

`download_chapter` 增加一个可选的 `failures` 列表参数来收集，不改变原有返回值，
现有调用方不受影响。

### 2.2 重试

```python
def retry_failures(failures, session, workers, delay, on_progress)
```

拿记录下来的直链重下。已存在的文件会被 `_download_one` 自动跳过，所以重复调用是安全的。

**一个已知限制**：manhuagui 的图片直链带时效签名（`sl.e` 是过期时间戳）。
如果本次下载跑了很久，记下的直链可能已过期，重试会失败。这种情况日志会显示，
重跑一次 `download` 即可（那会重新取直链）。不为此加复杂度。

### 2.3 入口

| 入口 | 形式 |
|---|---|
| WebUI | 第 2 步加「重试失败的 N 张」按钮，平时禁用，本次有失败项才亮 |
| CLI | `download --retry`，下载结束后自动重试一轮 |

WebUI 的按钮要注意：`_start()` 会 `reset()` 清掉 `JOB.failures`，所以投递重试
任务前必须先把清单取出来。

## 三、上一轮的 repair 怎么办

`repair` 已经实现并测试通过，是个独立命令，不影响默认流程。它能发现「末尾缺图」
这种本地看不出来的情况，但那不是本次要解决的问题。

**留着还是删掉交给用户定**，本轮不动它。

## 四、验收标准

1. 下载时人为造成失败，失败清单能正确记录（章节、序号、直链）
2. WebUI 按钮平时禁用，有失败项时亮起并显示张数
3. 点击后只重下失败的那几张，不重下整章
4. 重试成功后张数补齐
5. `--retry` 在 CLI 下同样生效
6. 没有失败项时按钮不亮、CLI 不做无用功
7. 不触碰任何已打包的 zip
