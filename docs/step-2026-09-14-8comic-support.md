## 二、破解 8comic 的过程

### 2.1 先走了一段弯路

最初 grep 页面发现 `<ul class="eps_list">` 是空的，判断「章节由 JS 动态填充」。
**这个判断是错的**——页面里有两个 `eps_list`，第一个是空壳，真正的 47 章在第二个。
章节其实是服务端直出的。

### 2.2 顺藤摸瓜

从 `comicview.js` 的 `cview()` 读出真实阅读页地址：非 VIP 会被送到
`articles.onemoreplace.tw`。再从章节页拿到 `var ti`（漫画 id）、`var chs`（章节数）
和一个 2292 字符的数据串，解码函数在 `j.js` 的 `lc` / `su` / `nn` / `mm`。

页面内联脚本里的变量名被混淆过（`wfp6_em7u4`、`p6of446`…），但骨架是固定的：
每章一条 47 字符定长记录，域名拆成十六进制片段藏在串尾。

### 2.3 怎么确保移植没猜错

**没有靠读代码猜**：先用 Node 执行站点原始 JS 得到标准答案，再用 Python 复刻，
然后**逐条比对全部 484 条 URL（47 章所有页面）——完全一致**。

## 三、踩到的三个坑

### 坑一：状态码 200 的伪装页

8comic 的章节页**不带 Referer 会返回一个 142KB 的伪装页**（WordPress 外观、
无任何漫画数据），而且**HTTP 状态码仍是 200**。

这是最阴险的一种反爬：不会触发任何异常，爬虫会静默跑空还以为成功了。
所以适配器在解析不到数据串时**显式报错**并直接点明「最常见原因是缺少 Referer」，
绝不当成空章节跳过。已写测试验证这条路径确实会报错。

### 坑二：中文全部乱码

首次 `list` 出来是 `åä¸è¬`。根因：8comic 响应头只有 `text/html`，
**不带 charset**，requests 按 RFC 默认成 ISO-8859-1。manwame 带了 `charset=utf-8`
所以一直没暴露这个问题。

修法：新增 `html_text(resp)`，响应头没声明 charset 时改信页面自报的编码，
两站共用。头里带 charset 的保持原样，manwame 行为不变。

### 坑三：混淆变量名不能依赖

数据串的变量名是站点构建时随机生成的。解析器改为按「页面里最长的那个字母数字串」
定位，并校验长度能容纳声明的章节数。站点换变量名不受影响。

## 四、一个白捡的性能提升

**同一部漫画的任意章节页，数据串完全相同且含全部章节**（已比对 ch=1 与 ch=2
逐字节一致）。所以整部漫画只需请求**一次**章节页就能算出全部章节的图片直链。

47 章从 47 次请求降到 1 次。适配器内按漫画 id 缓存，整部下载复用同一个 site 实例。

## 六、顺手修的小问题

`/api/chapters` 遇到不支持的站点原本返回 **502**（上游网关错误），
语义不对——贴错站点是用户输入问题。现在区分：选站点失败回 **400**，
抓取本身失败才回 502。

## 七、遗留风险

与 manwame 的 AES 密钥同理，8comic 的解码常量（记录长度 47、字段偏移、
片段区算式）也是从站点扒的，站点改算法即失效。缓解手段一致：
常量集中在类属性、不依赖混淆变量名、所有失败路径都有明确报错。
重新核对方法记在 README「维护提示」。
