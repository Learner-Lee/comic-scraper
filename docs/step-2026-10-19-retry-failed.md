## 一、先纠正上一轮的理解偏差

上一轮我把需求做大了：`repair` 去联网核对**全部历史章节**、还动已打包的 zip。
而实际要的只是——**本次这次下载里失败的图，重下那几张**。已经进了 `downloads/`
的 zip 说明当时就下齐了，不用再管。

纠正后实现简单得多，也更合适：失败项的直链、章节目录、序号本来就在内存里，
直接重试即可，**不用联网核对、不碰任何已完成的数据**。

## 二、实现

| 部件 | 说明 |
|---|---|
| `Failure` | 记一张失败的图：章节名、章节目录、序号、直链 |
| `download_chapter(..., failures=None)` | 可选参数收集失败项，不改原返回值，现有调用方不受影响 |
| `retry_failures(..., remaining=None)` | 拿记下的直链重下；仍没下来的收进 `remaining`，可以再试 |
| CLI | `download --retry`，下完自动重试一轮 |
| WebUI | 第 2 步「重试失败的 N 张」按钮，平时灰着，有失败项才亮 |

### 一个必须注意的时序

`_start()` 内部会 `reset()`，那会清空 `JOB.failures`。所以 `/api/retry` **必须在
抢槽之前**就把清单取出来，否则任务启动时清单已经没了。代码里标了注释。

## 三、已知限制（不为它加复杂度）

manhuagui 的图片直链带时效签名（`sl.e` 是过期时间戳）。本次下载跑太久的话，
记下的链接可能已过期，重试会失败。这种情况日志会写明，重跑一次 `download`
即可（会重新取直链）。
